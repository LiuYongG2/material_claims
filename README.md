# 工程物资领料履约诊断

## 我的判断

### 看到了什么
- 数据共 **1263 行**，但 `claim_id` 存在重复（12 条），`is_fulfilled` 有 **34 条为空**。
- `requested_at`（+08:00）与 `stock_synced_at`（UTC）**时区不一致**，直接用会算错库存同步延迟。
- 现场缺料落空（`is_fulfilled=0`）的申请，其**库存同步滞后**明显更长，且往往伴随**低账面库存**和**高当日单量**。

### 根问题
领料员看到的 `stock_qty` 是 `stock_synced_at` 时刻的账面快照。从同步到提交申请之间隔得越久，
这个数字越不可信；叠加仓库当日繁忙（`day_orders` 高）造成的出库竞争，就出现"系统显示有货、
到现场却没料"的空跑。**根问题不是库存少，而是库存信息陈旧 + 繁忙时段竞争。**

## 做了什么
1. **数据清洗**：时区统一（全部转 UTC 后计算差值）、按 `claim_id` 去重、剔除 `is_fulfilled` 空值。
2. **根因诊断**：对比落空/履约两组在 `sync_lag_min`、`stock_qty`、`day_orders` 上的分布。
3. **可执行阻断规则**：用三个风险因子（同步滞后 / 当日单量 / 账面库存）构造风险分，
   对高风险申请**提前阻断调拨**（花 15 工时），避免现场空跑（省 90 工时）。
4. **收益量化**：扫描不同阈值，选净节省工时最大的规则。

## 怎么证明有用（数字）
运行 `python analysis.py` 后，`outputs/metrics.json` 会输出以下数字（请以实际运行为准）：

- 有效样本数、落空单数、整体履约率
- 落空组 vs 履约组的 `sync_lag_min` / `stock_qty` / `day_orders` 中位数对比
- 最优阻断规则的：触发率、命中数、误伤数、精确率、召回率、**净节省工时**

成本口径：每次空跑损失 90 工时，每次提前阻断花费 15 工时。
